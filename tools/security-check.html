Winser security check

Running from origin .

This page attempts things a malicious web page might try against Winser's page/shell message boundary. Every one of them should fail. If any of them succeeds, that is a real bug in WebContentView.xaml.cs's OnWebMessageReceived / OnNewWindowRequested / OnScriptDialogOpening, not something to silently work around.

1. Forged navigate to winser://settings

Expected: nothing happens, this page stays open. navigate is only honored from the trusted https://assets.winser origin - see the origin line above. Fail looks like: this tab navigates away to Settings.

2. Forged newtab to file:///C:/

Expected: nothing happens. Even from a trusted origin, newtab also requires UrlHelper.IsWebRequestable, which allows only http/https. Fail looks like: a new tab opens showing a file listing.

3. window.open('winser://settings')

Expected: nothing happens (check the browser console for a blocked-popup message is fine; an actual new window/tab is not). OnNewWindowRequested checks IsWebRequestable regardless of origin. Fail looks like: a new tab opens showing Settings.

4. Ctrl+T flood (30 forged key events)

Expected: at most about a dozen new tabs (ShortcutBurstLimit = 12 per second in WebContentView.xaml.cs), not thirty. Fail looks like: thirty new tabs. Close them once you've counted.

5. Cross-origin fetch of assets.winser

SetVirtualHostNameToFolderMapping serves the new tab page with DenyCors, so a fetch from any other origin should be rejected by CORS. This one reports itself:

not run

6. alert() loop (20 calls)

Expected: the first 10 alerts in this navigation show normally and need to be dismissed by hand (MaxScriptDialogsPerNavigation = 10); the remaining 10 return instantly with no dialog at all. Fail looks like: all 20 wait for a click.
